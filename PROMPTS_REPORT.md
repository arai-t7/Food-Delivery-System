# Отчёт по заданиям из `promts`

## Промпт 1. Категории и профиль ресторана

### Исходный промпт

````text
You are an experienced full-stack developer.

I already have a Food Delivery System website. Do NOT change the existing design or break any current functionality. Only implement the following backend features while keeping the project structure clean and maintainable.

## Feature 1: Restaurant Categories Management (Backend)

Add the ability for restaurant owners to manage food categories from their restaurant profile.

Requirements:
- Each restaurant can have multiple categories.
- Create a Category model/table with:
  - id
  - restaurant_id (foreign key)
  - name
  - created_at
  - updated_at
- Only the owner of the restaurant can create, edit, or delete categories.
- Provide backend CRUD API endpoints:
  - Create category
  - Get all categories for a restaurant
  - Update category
  - Delete category
- Validate that category names are not empty.
- Prevent duplicate category names within the same restaurant.
- When categories are requested, return them sorted alphabetically.

## Feature 2: Restaurant Registration/Profile

Extend the restaurant registration/profile functionality.

Requirements:
- During restaurant registration or profile editing, allow the owner to enter:
  - Restaurant name
  - Restaurant description
  - Address
  - Phone number
  - Opening hours
  - Restaurant logo/image (if image upload already exists, reuse it)
- Save all information in the database.
- Add validation for required fields.
- Allow restaurant owners to edit their profile after registration.
- Only authenticated restaurant owners can modify their own profile.
- Existing users and restaurants should continue working without issues.

## General Requirements

- Do not remove or modify existing functionality.
- Keep the current UI style.
- Follow the project's coding style and architecture.
- Add database migrations if needed.
- Update models, controllers, routes, services, and database schema where necessary.
- Make sure all new endpoints are properly secured.
- Ensure the application runs without errors after implementing these features.ё
````

### Что выполнено

- Добавлены профиль ресторана, связь с владельцем и сохранение названия, описания, адреса, телефона, часов работы и ссылки на логотип. Профиль редактируется через `PUT /api/restaurants/mine`.
- Добавлены связи категорий с рестораном и даты создания и изменения. Список доступен через `GET /api/restaurants/{restaurant_id}/categories`, операции записи через `/api/restaurants/mine/categories`. API проверяет владельца, отсекает пустые названия и запрещает дубликаты без учёта регистра. Список возвращается в алфавитном порядке.
- При запуске миграция переносит существующее меню и заказы в профиль «Демо-кухня» с сохранением идентификаторов. Для удаления категории с блюдами нужно сначала перенести или удалить эти блюда.

## Промпт 2. Split the Bill и Mystery Meal

### Исходный промпт

````text
[26.11.2026 10:52] РизаСултан:
Forwarded from arai
features:split the bill(возможность разделить общую стоимость заказа между несколькими людьми с помощью простого калькулятора), mystery meal(пользователь выбирает бюджет, а приложение случайным образом предлагает блюдо в пределах этой суммы)
````

### Что выполнено

- В чеке появился калькулятор на заданное число человек. Остаток распределяется по одному тенге между несколькими участниками. Сумма всех долей совпадает с итогом чека.
- В меню ресторана можно сгенерировать случайное доступное блюдо в пределах бюджета и выбранной категории, повторить подбор и добавить результат в чек.

## Промпт 3. Рестораны, витрина, корзина и случайные наборы

### Исходный промпт

````text
[26.11.2026 11:03] РизаСултан: Ты — опытный full-stack разработчик.

# Задача: Расширение функционала Food Delivery System (Рестораны, категории меню, главная страница, Split the Bill и Mystery Meal)

## Контекст текущего проекта
У нас уже есть работающее веб-приложение для доставки еды. Сейчас в системе реализованы:
- Авторизация и ролевая модель для 4 ролей: Клиент (Client), Шеф-повар (Chef), Курьер (Courier) и Администратор (Admin).
- Базовый флоу заказа: клиент может оформлять заказ и отслеживать его текущий статус.

Критически важно: НЕ меняй существующий дизайн и стиль интерфейса, НЕ удаляй и НЕ ломай текущую логику авторизации, ролей и отслеживания статусов заказов. Аккуратно интегрируй новый функционал поверх существующей базы, соблюдая стиль кода и архитектуру проекта.

---

## Функционал 1: Регистрация и профиль ресторана (Backend + UI)
Добавь возможность зарегистрироваться и войти в систему под ролью Ресторан (Restaurant), а также управлять профилем заведения.

Требования:
- При регистрации ресторана и при последующем редактировании профиля владелец должен иметь возможность указать и сохранить в БД:
  - Название ресторана (`name`)
  - Описание ресторана (`description`)
  - Адрес (`address`)
  - Номер телефона (`phone`)
  - Часы работы (`opening_hours`)
  - Логотип / обложку ресторана (`logo` / изображение — если загрузка изображений уже реализована в проекте, переиспользуй её, иначе поддержи ссылку/загрузку).
- Добавь валидацию обязательных полей.
- Разреши владельцам ресторанов редактировать свой профиль после регистрации.
- Безопасность: Редактировать профиль ресторана может только авторизованный владелец этого конкретного ресторана.
- Существующие пользователи и роли должны продолжать работать без сбоев.

---

## Функционал 2: Управление категориями блюд ресторана (Backend + UI)
Добавь для владельцев ресторанов возможность создавать и настраивать собственные категории меню прямо из профиля / кабинета ресторана.

Требования:
- Каждый ресторан может иметь множество категорий.
- Создай модель / таблицу Category в базе данных со следующими полями:
  - id
  - restaurant_id (внешний ключ / foreign key на ресторан)
  - name
  - created_at
  - updated_at
- Создай CRUD API эндпоинты на бэкенде:
  - Создание категории
  - Получение всех категорий конкретного ресторана
  - Обновление категории
  - Удаление категории
- Валидация и правила:
  - Создавать, редактировать и удалять категории может только владелец данного ресторана.
  - Название категории не может быть пустым.
  - Запрети дубликаты названий категорий внутри одного и того же ресторана.
  - При запросе списка категорий возвращай их отсортированными в алфавитном порядке.

---

## Функционал 3: Управление блюдами ресторана (Dashboard)
Реализуй в личном кабинете ресторана интерфейс и логику управления меню.

Требования:
- CRUD для блюд: Авторизованный ресторан может добавлять новые блюда (название, описание, цена, привязка к созданной category_id этого ресторана, фото, статус наличия), редактировать существующие и удалять их.
- Каждое блюдо должно быть жестко привязано к restaurant_id заведения, которое его создало.
- Изменять или удалять блюда может только владелец ресторана-создателя.

---

## Функционал 4: Обновление главной страницы (Витрина ресторанов)
Перестрой точку входа для покупателя на каталог заведений.

Требования:
- Первый экран для пользователя: Сделай главной страницей сайта (home / landing page при открытии или после входа клиента) каталог выбора ресторанов, а не общий список всех блюд.
- Карточки ресторанов: Отобрази список всех зарегистрированных ресторанов в виде карточек в текущем стиле дизайна (логотип/обложка, название, описание, адрес, часы работы).
- Страница меню заведения: При клике на карточку ресторана открывается страница конкретного заведения, где отображаются только блюда этого ресторана, сгруппированные или фильтруемые по его категориям.
- Связь с заказом: Клиент выбирает блюда внутри выбранного ресторана, добавляет их в корзину и оформляет заказ по уже существующей логике (заказ должен сохранять привязку к ресторану).

---

## Функционал 5:
[26.11.2026 11:03] РизаСултан: Split the Bill (Калькулятор разделения счета)
Добавь удобный и простой калькулятор для разделения общей стоимости заказа между несколькими людьми.

Требования:
- Пользователь может указать количество человек (`N`), между которыми делится сумма заказа (например, на странице корзины/оформления заказа или прямо в виджете заказа).
- Автоматически рассчитывай и отображай сумму на одного человека (корректно обрабатывая округление/копейки или остаток, чтобы сумма долей не терялась и не вызывала путаницы).
- Опционально поддержи быстрый пересчет при изменении состава корзины или количества человек, без усложнения интерфейса.

---

## Функционал 6: Mystery Meal (Случайный выбор позиции и сборка случайного сета по бюджету)
Реализуй интерактивный режим Mystery Meal, где пользователь задает бюджет, а система подбирает варианты с учетом реальных позиций в базе и их цен.

Требования:
- Режим 1 — Случайная позиция по бюджету:
  - Пользователь выбирает максимальный бюджет (или ценовой диапазон) и тип позиции — например: любое случайное блюдо, напиток, салат, горячее / основное или другую доступную категорию/тип позиции (опираясь на реальные позиции из БД/меню, которые вписываются в заданный бюджет и доступны для заказа).
  - Система случайно выбирает подходящую позицию в рамках бюджета и предлагает добавить её в заказ (или перегенерировать вариант).
  - Если в указанном бюджете по выбранному типу позиций ничего нет — выведи понятное сообщение и предложи увеличить бюджет или сменить тип позиции.
- Режим 2 — Случайный сет (набор блюд) в рамках бюджета:
  - Пользователь задает бюджет и выбирает конфигурацию сета:
    - Напиток + Салат + Второе
    - Напиток + Салат + Первое
    - Напиток + Салат + Первое и Второе (оба) (либо гибкий выбор включаемых компонентов сета: напиток, салат, первое, второе).
  - Система подбирает случайную комбинацию позиций под выбранную структуру сета так, чтобы суммарная стоимость укладывалась в заданный бюджет пользователя (по возможности используя реальные позиции из меню).
  - Пользователь может просмотреть состав подобранного сета, итоговую цену, пересобрать вариант или добавить весь сет в заказ.

---

## Общие технические требования
- Не удаляй и не изменяй существующий функционал.
- Сохрани текущий UI-стиль проекта.
- Следуй принятому в проекте стилю кода и архитектуре.
- При необходимости создай и примени миграции базы данных.
- Обнови модели, контроллеры, роуты, сервисы и схему БД там, где это необходимо.
- Убедись, что все новые эндпоинты надежно защищены проверками авторизации и прав доступа.
- Проверь, что после внесения всех изменений приложение запускается и работает без ошибок.
````

### Что выполнено

1. **Регистрация и профиль.** В форме регистрации есть выбор роли «Ресторан». Вход использует общую форму, профиль редактируется в кабинете. Для логотипа поддерживается необязательная ссылка HTTP(S). Миграция подставляет явные значения «Не указан» и «Не указаны» там, где у демо-кухни не было контактных данных.
2. **Категории.** Из кабинета можно просматривать, добавлять, редактировать и удалять пустые категории. Тип категории используется при подборе случайных наборов.
3. **Блюда.** Кабинет поддерживает CRUD с ценой, категорией своего ресторана, ссылкой на фото и доступностью. После удаления блюда история заказов сохраняет название, цену и количество.
4. **Витрина и заказ.** Гости и клиенты открывают каталог ресторанов. Из карточки можно открыть меню выбранного ресторана и фильтровать блюда по категориям. Для оформления требуется вход клиента. Чек содержит блюда одного ресторана, его идентификатор сохраняется в заказе. Кухня видит свои заказы, администратор и курьер продолжают использовать свои очереди и статусы. Колесо фортуны доступно в меню ресторана.
5. **Split the Bill.** Калькулятор встроен в чек и пересчитывается при изменении суммы или числа участников. Расчёт ведётся в целых тенге, как и цены проекта.
6. **Mystery Meal.** Поддерживаются одна позиция и все три запрошенных варианта сета. Подбор использует доступные блюда текущего ресторана, резервирует стоимость минимальных вариантов для оставшихся компонентов и соблюдает бюджет. Интерфейс показывает состав и итог, позволяет пересобрать сет и добавить его в чек одним запросом. Если подходящего варианта нет, предлагает изменить условия.

## Проверки

- SQLite запущена с чистой и старой схемой. Проверены миграция, регистрация и вход, операции с профилем и меню, запрет изменений чужим владельцем, добавление сета целиком, заказ и переходы статусов до доставки.
- Миграция PostgreSQL проверена на отдельной БД со старой схемой, включая повторный запуск миграции, сохранение всех 35 блюд и возможность использовать одинаковые названия категорий в разных ресторанах.
- В Chrome проверены витрина для гостя, переход в меню, оба режима Mystery Meal, добавление набора, деление с остатком и кабинет владельца. Экраны просмотрены при ширине 390, 768 и 1440 пикселей.
- `npm run lint`, `npm run build` и `git diff --check` прошли.
